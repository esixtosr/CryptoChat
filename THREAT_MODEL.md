# CryptoChat - Threat Model & Security Analysis

Author: Edwin Sixtos Ruiz  
Course Project: Secure Messaging Application

CryptoChat is an educational end-to-end encrypted messaging project built with PyQt6, X25519, HKDF-SHA256, and AES-256-GCM. This document describes what the app protects, what it assumes, and what it intentionally does not try to solve.

CryptoChat is not a production Signal replacement. It is a focused portfolio project for secure messaging fundamentals.

## Security Goals

- Confidentiality: passive network observers should not read message plaintext.
- Integrity and authenticity: modified or forged ciphertext should fail AES-GCM authentication.
- Key separation: each traffic direction uses a different AES-GCM key.
- Replay protection: duplicate, old, future, or tampered message counters are rejected.
- Peer verification: users can compare public-key fingerprints and persist trusted fingerprints per contact.
- Clear user feedback: the GUI shows display names, connection state, local fingerprint, peer fingerprint, and trust status.

## Assumptions

- The devices running CryptoChat are not compromised.
- Python, PyQt6, the operating system, and the `cryptography` package behave correctly.
- X25519, HKDF-SHA256, and AES-256-GCM remain cryptographically secure.
- Users verify fingerprints over a trusted out-of-band channel before sending sensitive messages.
- Display names are convenience labels only; they are not trusted security identities.
- The local per-user `trusted_contacts.json` file is available and has not been maliciously edited.
- The attacker can observe, drop, replay, reorder, modify, or inject network traffic.

## Adversary Models

### Passive Network Attacker

Capabilities:

- Watches all TCP traffic.
- Records ciphertext for later analysis.

Mitigations:

- Message plaintext is encrypted with AES-256-GCM.
- Session keys are derived from ephemeral X25519 shared secrets.
- Network captures reveal framed ciphertext, not readable chat messages.

### Active Network Attacker

Capabilities:

- Modifies, injects, drops, reorders, or replays packets.
- Attempts a man-in-the-middle public-key substitution during handshake.

Mitigations:

- AES-GCM rejects modified ciphertext and authenticated data.
- Strict counters reject replayed and out-of-order packets.
- TOFU fingerprint verification helps detect public-key substitution.
- Saved fingerprints are checked on future connections, and mismatches block sending.
- Encrypted display-name exchange improves usability but does not replace fingerprint verification.

### Replay Attacker

Capabilities:

- Captures valid encrypted packets and sends them again.
- Sends packets out of order or skips ahead to future counters.

Mitigations:

- Each packet includes an 8-byte counter.
- The counter is authenticated as AES-GCM associated data.
- The receiver accepts only the next expected counter.
- The receive counter advances only after successful authentication and decryption.

### Local Device Attacker

Capabilities:

- Reads local files, memory, process state, or keystrokes.
- Modifies the per-user `trusted_contacts.json` trust file.

Mitigation:

- Local device compromise is out of scope for this project.
- CryptoChat does not provide secure key storage, malware resistance, memory hardening, or operating-system sandboxing.

## Implementation Mitigations

- Directional keys: HKDF derives separate client-to-server and server-to-client AES-GCM keys under the `CryptoChat-v1` protocol context.
- Nonce safety: each direction starts its own counter at zero, but under a different AES-GCM key.
- Authenticated counters: packet counters are included in AES-GCM associated data.
- Fail-closed decrypts: failed authentication does not advance the receive counter.
- Safer framing: TCP frames have a maximum size and invalid lengths cause disconnect/error behavior.
- Persistent TOFU: accepted fingerprints are saved per contact and checked on reconnection.
- Send gating: messages cannot be sent without an active encrypted session and verified fingerprint.
- Display names: each peer sends an encrypted post-handshake name label, but trust still depends on the fingerprint.

## Known Limitations

- No long-term identity keys. Fingerprints are tied to the current public key generated by the app session.
- No group messaging.
- No offline message queue, delivery receipts, or message database.
- No file transfer.
- No padding, so approximate message sizes are visible.
- No protection if the endpoint device is compromised.
- No password-based local encryption for the trust store.
- No certificate authority, web-of-trust, or production PKI.
- No post-compromise recovery or double-ratchet message-key rotation.
- No formal protocol audit.

## What CryptoChat Does Not Protect Against

- Malware, keyloggers, screen capture, or memory scraping on either device.
- A user accepting the wrong fingerprint during first use.
- A peer choosing a misleading display name.
- A malicious local user editing or deleting the per-user `trusted_contacts.json` trust file.
- Traffic analysis based on connection timing, IP addresses, or message sizes.
- Denial-of-service attacks where an attacker drops traffic or forces disconnects.

## Conclusion

CryptoChat demonstrates modern secure messaging building blocks in a compact, understandable Python project: X25519 key exchange, HKDF key derivation, AES-GCM authenticated encryption, directional key separation, explicit replay protection, TOFU fingerprint verification, and a GUI that makes trust state visible.

Its scope is intentionally educational and portfolio-focused. The design is strong enough to explain the sharp edges of applied cryptography while remaining honest about what a small class project cannot provide.
